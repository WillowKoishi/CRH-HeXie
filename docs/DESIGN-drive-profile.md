# 驱动建模：改为「实测标定曲线」

## 〇、放弃上一版思路

上一版（用指令 u 和速度 v 建二维表、推测加速度）是错的：
它在**假设**驱动行为，而驱动方式千差万别，假设必然失真。

正确思路：

> **不建模驱动，直接测量这辆车"实际怎么加速、怎么停"。**

## 一、模型

每辆车保存三条**实测曲线**（都是 v(t)，t 为 tick）：

    ACCEL  : 0 → 满速，全油门
    COAST  : 满速 → 0，全松油门（自然阻力）
    BRAKE  : 满速 → 0，全刹车

由曲线可反推任意速度下的加速度：

    a_accel(v) = dv/dt   在 ACCEL 曲线上取 v 附近
    a_coast(v) = dv/dt   在 COAST 曲线上取
    a_brake(v) = dv/dt   在 BRAKE 曲线上取

不需要知道是转轴、推进器还是帆。

## 二、标定（学习）过程

触发条件（全自动检测）：

    列车静止（|v| < 0.05）
    且 指令为满油门（u = 1）
    → 开始记录 ACCEL，每 tick 采样一次 v
    → 当 v 连续 20 tick 不再上升（或达到平台）→ 记录结束，vmax = 最大观测值

    松油门且列车在动 → 记录 COAST
    满刹车且列车在动 → 记录 BRAKE

也就是"造好车之后跟着跑一趟"，走完自然就有了。

## 三、回放（物理体不在场时）

    if (u > 0)      a =  u * a_accel(v)
    else if (u < 0) a = -|u| * a_brake(v)
    else            a = -a_coast(v)          // 注意 coast 本身是负的

    v += a * dt
    s += v * dt

速度上限由实测的 `vmax` 决定。

## 四、数据结构

    final class DriveProfile {
        double vmax;             // 实测满速
        float[] accelV;          // 下标 = tick，值 = 该 tick 的速度
        float[] coastV;
        float[] brakeV;
    }

- 每 tick 一个 float，加速段按 200 tick（10 秒）算，约 800 字节/条
- 三条曲线 ≈ 2.4 KB/车，存 NBT 完全可接受

## 五、为什么这比"建驱动力模型"可靠

| | 力模型 | 实测曲线 |
|---|---|---|
| 需要知道驱动类型 | 是 | **否** |
| 换驱动（轴→推进器） | 要重写公式 | 重跑一次即可 |
| 载重/摩擦/坡度影响 | 需建模 | **自动包含在曲线里** |
| 精度 | 取决于模型假设 | 取决于实测精度 |
| 失败模式 | 算不出来就完全不对 | 最多是这条曲线不适用 |

## 六、必须在文档里写清的代价

1. **每辆车要跑一趟标定**（玩家负担）
2. 曲线绑定**当时的载重与编组**；加了车厢/装了货要重测
3. 曲线绑定**标定时的线路**（坡度包含在内）；换线路后坡度分量不再准确
4. 碰撞、脱轨等异常无法预测

## 七、待确认

- 标定是**自动检测**还是玩家在界面里点"开始记录"
- 部分油门（|u| < 1）是否近似按线性缩放
- 曲线是否需要对坡度做补偿（补偿 = 需要坡度数据；不补偿 = 曲线只管那条线路）
