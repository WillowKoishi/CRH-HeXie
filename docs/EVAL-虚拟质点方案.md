# 方案评估：轨道约束的"虚拟质点" + 进场传送物理体

提出者思路：
  新建一个 tick 点，赋予物理意义（质量/速度），用轨道约束其轨迹；
  进入加载范围时把物理体传送过来。
  目标：既保住物理体运动状态，又能出加载范围运行。

以下为可行性评估，所有 API 结论均来自 javap 实测。

---

## 一、可行性支点：Sable 提供了什么

| API | 结论 |
|---|---|
| `RigidBodyHandle.teleport(Vector3dc pos, Quaterniondc rot)` | ✅ **可直接传送刚体** |
| `RigidBodyHandle.addLinearAndAngularVelocity(Vector3dc, Vector3dc)` | ✅ 可加线/角速度（注意是 add，不是 set，需先减当前值） |
| `RigidBodyHandle.getLinearVelocity()` / `getAngularVelocity()` | ✅ 可读速度 |
| `SubLevel.logicalPose()` → `Pose3d` | ✅ 返回可写姿态对象 |
| `ServerSubLevelContainer.addForceLoadTicket(...)` | ✅ 已有，本模组正在使用 |
| `ServerSubLevelContainer.getHoldingChunkMap()` | ✅ 可访问 HoldingSubLevel 存档态 |
| **HoldingSubLevel → 活体（重新加入世界）** | ❓ **未找到公开 API**（只看到 `removeSubLevel`，没看到对称的 add） |
| 传送后物理是否稳定（是否抖动/回弹） | ❓ 未知，必须实测 |

**结论：核心动作（传送 + 设速度）有 API；但"从卸载态恢复成活体"这一步没有找到公开入口。**
这是整个方案的第一道生死线。

---

## 二、工作量拆解

### 模块 1：轨道约束的运动状态（中等）

- 位置表示：直接复用 Create 的 `TravellingPoint`（node + edge + position），无需自造
- 状态量：`s`（沿路径里程）、`v`（沿轨速度）、`m`（质量，取自 `MassTracker` 或模组配置）
- 积分：`v' = (F_牵引 - F_阻力 - F_坡度 - F_制动) / m`；`s' = v`
- **难点：F_牵引**。要从转速推轮周牵引力，需要齿轮比、轮半径、传动效率——这些参数目前**没有任何来源**，只能自己定一套并接受"不真实但自洽"

预估：**250～350 行**，其中牵引力模型需要反复调参。

### 模块 2：s → 车体姿态（中等，可抄）

给定前后两点的轨道位置，算出车体中心、yaw、pitch。
Create 自己就是这么干的——`Carriage.updateContraptionAnchors` 里有现成实现
（`positionAnchor`、`Mth.atan2(diffZ, diffX)`、pitch 计算），可直接照抄。

预估：**120～180 行**。

### 模块 3：交接（高风险）

**出场（进入加载范围）**
1. 确认子结构是活体（HoldingSubLevel 需先恢复 —— 见第一节问号）
2. `handle.teleport(目标位置, 目标朝向四元数)`
3. 速度对齐：先读当前速度，`addLinearAndAngularVelocity(目标速度 - 当前速度, ...)`
4. 等待 1～2 tick 观察是否稳定

**入场（离开加载范围）**
1. 从 handle 读 pose + 速度
2. 反解成 `s`（沿轨道投影）与 `v`（沿切线投影）
3. 保存到我们的状态里

预估：**150～200 行**，但**调试时间远大于代码量**。

### 模块 4：两套积分器的一致性（最高风险）

物理体由 Sable 积分（重力、摩擦、碰撞、约束求解），
我们的模型是简化 1D 积分。两者**本质不可能完全一致**。

后果：每次交接都会有一个速度/位置的突变。
必须设计成"交接时以在场者为权威、另一方无条件接受"，而不是试图让两套结果相等。

预估：**无代码量，但这是整个方案的成败点。**

## 三、总量与难度评级

| 项 | 估计 |
|---|---|
| 新增代码 | **700～900 行** |
| 需要改动的现有模块 | `TrainDispatcherBlockEntity`（驾驶层）、`TrainBinder`（可能要重写）、新增 1～2 个类 |
| 编码工作量 | 中 |
| 调试/标定工作量 | **高**（两套积分 + 传送稳定性 + 边界情况） |
| 前置未知数 | **2 个致命**：卸载态恢复、传送后稳定性 |
| 总体难度 | **高**（不是"难在写"，是"难在调"） |

## 四、必须先做的验证（Spike，约 100 行，1 次游戏内测试）

在写任何正式代码之前，用调试命令验证三件事：

1. **传送**：对一列活体子结构执行 `handle.teleport(pos+10, 当前朝向)`，观察
   - 是否瞬移
   - 1 秒后是否回弹/抖动
   - 区块是否跟着加载
2. **速度设置**：`addLinearAndAngularVelocity` 能否精确置速，是否被物理立刻改写
3. **卸载恢复**：让子结构走出加载范围 → 查 `getHoldingChunkMap()` 里是否有它 →
   尝试恢复（若无 API，此项直接判死）

**若第 3 项无解，本方案退化为"必须常加载"（方案 B），整条路线要重新评估。**

---

## 五、必须先排上的对照方案：常加载（更简单）

既然本模组已经在用 `addForceLoadTicket`，有一个成本更低的选项：

**让子结构所在的区块（就它占的那几个）永远保持加载。**

- 车厢包围盒只有几个方块 → 常加载的区块数是个位数
- 不需要 1D 模型、不需要传送、不需要交接
- 物理永远在线，速度传感器读数永远有效
- 代价：列车所在位置的区块常驻内存（随列车移动而移动，不是全线路）

**如果这个开销可接受，它能直接满足"出加载范围继续跑"，且完全不违反物理体权威。**

唯一要验证的是：`addForceLoadTicket` 是否真的能让 `isChunkLoadedEnough` 通过、
从而让子结构不被踢进 `HoldingSubLevel`。

---

## 六、建议顺序

1. 先测 **常加载能不能保住物理体**（半天，零新代码，只加日志）
2. 如果不行，再上"虚拟质点"方案，并先做第四节的三项 Spike
3. 不要在 Spike 通过前写任何正式代码
